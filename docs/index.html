The problem

Every release, the suite drifts away from the app

On a live project, each release changes the UI. Some test failures mean the release changed something on purpose. Others mean it broke something. Telling those apart by hand is slow, and getting it wrong is costly in both directions. A regression accepted as "the new behaviour" ships to production. An intended change reported as a bug wastes a developer's afternoon.

The paperwork adds up too: reading every ticket in the release, writing tests, keeping test IDs and docs consistent, commenting on and transitioning tickets, filing bugs with evidence, and writing a release report.

The approach I took was to let an agent do the exploration, test writing and bookkeeping, and to keep every judgement call with the QA analyst. The rule that holds it together:

The ticket says what was intended. The app says what exists. Where they disagree, the app wins, and the disagreement is reported as a finding. It is never resolved silently.

How it works

Thirteen steps, three gates, one draft file

At each gate the agent writes its proposals to a draft Markdown file with checkboxes, then stops. The analyst ticks boxes and edits drafted cases in that file. A box left unticked counts as a question, never as approval.

  1. 1

    Intakeagent

    Pull every ticket in the fixVersion from Jira, including tickets held by an earlier run.

  2. 2

    Triageagent

    Sort each ticket: testable, too thin (no usable acceptance criteria), no browser-visible change (checked against git), or already covered.

  3. 3

    Baseline runagent

    Run the whole suite against the deployed release and classify every unexpected failure.

  4. 4

    Group by areaagent

    Map changed files to routes using git history and the project's app map.

  5. 5

    Explore the live appagent

    Walk each area in a real browser through Playwright MCP. Every mismatch with the ticket becomes a numbered finding with a screenshot.

  6. 6

    Gate 1: coverage impactanalyst

    Which tickets proceed, how to read each undecided failure, answers to open questions.

  7. 7

    Gate 2: drafted testsanalyst

    Approve, edit or reject each proposed test case and the script plan.

  8. 8

    Write testsagent

    Page objects and specs, using IDs scoped to the ticket.

  9. 9

    Run to greenagent

    At most 3 fix attempts per test, then re-run every spec that uses a changed page object.

  10. 10

    Reconcileagent

    Regenerate the test index and Jira mapping, and stage screenshots for attaching.

  11. 11

    Gate 3: decisionsanalyst

    Pass, fail or hold per ticket. File a bug, not a bug, or known per finding. Release sign-off.

  12. 12

    Publish the reportagent, after approval

    A per-ticket QA coverage report, created or updated in Confluence.

  13. 13

    Jira actionsagent, after approval

    Bugs first (duplicate-checked, then linked), then transitions and evidence comments. The analyst approves the whole batch first.

The core judgement

Is a red test an intended change or a regression?

Every unexpected failure in the baseline run lands in one class, and each class requires specific evidence. When the evidence is ambiguous, the agent doesn't pick. It hands the call to the analyst.

ClassEvidence requiredWhat happens
Intended changeA ticket in this release describes the new behaviour, and the app shows exactly that.The test update is proposed at Gate 1, citing the ticket and AC. The test is tagged with that ticket.
Test mechanicsBehaviour is unchanged, but markup, role or position moved, so the locator no longer matches.The locator is fixed without approval. What the test asserts must not change.
Possible regressionBehaviour differs from the test, and no ticket in scope accounts for it.The test is left alone. The failure is reported and linked to the likely ticket through git history, with a confidence level.
EnvironmentSession expiry, fixture drift, leftover data, a toolchain crash, or the suite running ahead of the deployed build.The test or fixture is fixed, and an ISS-TS-<slug> entry is logged.
UndecidedThe evidence fits two classes.Listed at Gate 1 with both candidates. The analyst decides.

Design decisions

Guardrails built into the design

Never test unseen behaviour

A ticket marked Done may not be deployed. Tests are written only for behaviour observed in the live app. Tests written from ticket text alone can read perfectly and test nothing.

No invented acceptance criteria

If a ticket has no usable ACs, it becomes a question at Gate 1. A made-up AC turns into a test asserting something nobody agreed to, and it looks as trustworthy as every other test.

"How" versus "what"

The agent may change how a test finds things (locators, waits) on its own. It may change what a test expects only with a ticket or the analyst's approval. It never weakens an assertion to get a green run.

Write tools not pre-approved

Jira and Confluence read tools are pre-approved. Write tools are left off on purpose, so every external write raises a permission prompt as well as passing Gate 3.

Credentials kept out of context

Deny rules block the Read tool on .env and the saved login. A PreToolUse hook closes the shell gap (cat, Get-Content, cp).

IDs that never collide

Tests are numbered within their ticket (PROJ-327-2), not from a shared counter. Two branches or agent runs can't pick the same ID, and nothing ever needs renumbering.

Under the hood

The spec is the record; the docs are generated

Each test carries a one-line docstring in a fixed format: ID, title, ticket and AC, type, priority. A plain-language Verifies line follows for non-technical readers.

qa-ledger is a dependency-free Node script. It parses the specs statically, checks every ID and docstring, and regenerates the test index, the Jira-to-test mapping and the summary blocks in the suite's README and CLAUDE.md. It normalises line endings so the staleness check works on Windows checkouts. --check fails CI when anything is stale or malformed.

qa-baseline reads Playwright's JSON report and lists every unexpected result. It flags test.fail() tests that started passing, which means a known bug looks fixed.

Suite conventions

  • Page Object Model with no selectors in spec files. Methods are named for what the user does, so the spec reads as the test's steps.
  • Sequential, single-worker runs against the shared live environment, so tests don't collide on data or logins.
  • Login cached and reused only while its remaining lifetime covers a whole run.
  • test.fail() marks a test that asserts correct behaviour against a known bug. It turns red when the bug is fixed.
  • Records the suite creates use a fixed prefix and are cleaned up before and after each run.

What it deliberately doesn't do

  • Write to Jira or Confluence before Gate 3.
  • Change what an existing test expects without a ticket or approval.
  • Retry a flaky test into a pass, or add blind waitForTimeout calls.
  • Check calculations, performance or security. Those belong in backend tests.
  • Upload attachments or rank the backlog. It lists both for the analyst instead.

QA-LESSONS.md

Problems the suite already paid for, written down as rules

The kit ships 17 rules taken from a mature suite. Each one says what to watch for, why it matters, and what enforces it. The agent re-reads them before writing any locator or wait. A selection:

playwright-isvisible-is-one-shot

isVisible({ timeout }) ignores the timeout. Right after a navigation it reads false off a loading skeleton, which silently breaks cleanup guards.

the-suite-can-be-ahead-of-the-deployed-app

Check git log before calling a failure a regression. The spec may already carry a later ticket's change that isn't deployed yet.

an-expected-fail-test-must-fail-for-the-right-reason

A test.fail() test passes on any failure, including a broken locator. Run it as a plain test first and read the error.

a-cli-reporter-replaces-the-config-reporters

--reporter=line drops the JSON report, so the baseline summary would silently describe the previous run.

hydration-can-wipe-early-input

On server-rendered React apps, text typed right after page load can be erased by hydration. Search helpers re-type inside the polling wait.

prefer-behaviour-assertions-size-coverage-to-risk

Assert outcomes (values, URL state, counts), not that an element is visible. Size the number of cases to risk, not to a quota.

Reusable on any project

From one project's tool to a kit for any project

The Anser version was wired into that project's routes, priorities and release pipeline. For the kit, I moved every project-specific value into config and made the Anser-only features optional.

To adopt it, a project changes five things

workflow.toml

Jira site, project key and QA status names, priority map, test URL, Confluence pages.

scripts/utils/auth.ts

The login route and form locators.

scripts/pages/HomePage.ts

One element that proves the landing page has rendered.

playwright-qa/CLAUDE.md

The app map: how source files map to routes, look-alike pages, UI library quirks, test roles.

SKILL.md frontmatter

The Atlassian tool prefix, only if the project uses a different MCP server.

Everything else installs unchanged: the skill and its 7 reference files, the ledger and baseline scripts, the security hook, and the starter lessons. The first run is a single ticket. A full release comes after that.
